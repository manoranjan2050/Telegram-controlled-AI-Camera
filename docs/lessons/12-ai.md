# Lesson 12 — AI Object Detection (Phase 14)

## Goal

Establish the `telegramp4_ai` abstraction, ready for a real model once one is
selected and verified.

## ⚠️ Hardware/model verification status

Choosing and verifying a model needs: a decision on the inference framework
(most likely Espressif's **ESP-DL** with a small quantized detection model,
though this hasn't been confirmed against what's practical on ESP32-P4's
PSRAM budget), the Phase 5 camera pipeline actually working (to get images
in), and real hardware measurement of inference time and memory footprint.
None of this has been done in this session — `telegramp4_ai_process_image()`
is an honest stub returning `ESP_ERR_NOT_SUPPORTED`. **Do not claim a model
works until it has actually run inference on hardware and the time/memory
numbers have been measured** — see [memory-and-performance.md](memory-and-performance.md).

## What you learn

- Keeping AI compile/config-time optional (`TELEGRAMP4_AI_ENABLED`, default
  off) so the rest of the firmware works identically without it
- Shaping the result type (`telegramp4_ai_result_t`: labeled detections +
  confidence + inference time) before the model exists, so the Telegram-facing
  code (Phase 15) can be written and tested independently of model choice

## Phase 15 update — Telegram AI workflow

`/ai` (`main/app_main.cpp`'s `handler_ai()`) ties the pieces together: capture
via `telegramp4_camera`, run `telegramp4_ai_process_image()`, then send both
the photo and a formatted result:
```
🤖 AI Detection

Detected:
Person - 94%
Laptop - 88%

Inference:
142 ms
```
If AI is disabled via Kconfig, `/ai` replies cleanly explaining that instead of
attempting inference. Today, with the stub in place, it reports
`❌ AI inference failed: model not yet verified on this hardware.` — correct,
honest behavior until Phase 14's model verification is done. The "🤖 AI
Detect" menu button (Phase 4's stub) calls this exact same `handler_ai()`.

## Phase 16 update — AI on Telegram photos

When a photo arrives (Phase 10), after the existing "Image received" reply,
`on_photo_received()` now also sends a follow-up keyboard:
```
What would you like to do?

[🤖 Detect Objects] [💾 Save] [🗑 Delete]
```
Each button's `callback_data` encodes the action and the already-saved
filename (`"/received_ai <name>"`, `"/received_save <name>"`,
`"/received_delete <name>"`), dispatched through the same command registry as
everything else. "Detect Objects" (`handler_received_ai`) reads the file back
from `/sdcard/received/`, runs it through `telegramp4_ai_process_image()`
(same honest-stub behavior as `/ai` until Phase 14's model lands), and reports
results. "Save" is a no-op acknowledgment (the file is already persisted the
moment it's received — Phase 10's behavior). "Delete" removes it, sanitized
the same way as every other file operation.
